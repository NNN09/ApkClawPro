# ApkClaw 产品迭代规划（Roadmap）

> 版本：v0.1（草案） ｜ 日期：2026-09-02 ｜ 基线：`feat/persona-session-memory-skills` 分支
> 说明：本文档基于当前代码能力盘点产出，功能编号 F1–F13 供后续排期与追踪引用。

---

## 1. 产品定位

**把个人 AI Agent 装进真实 Android 设备里执行**：设备既是 Agent 的运行载体，又是被操控的对象。用户通过消息渠道（钉钉 / 飞书 / QQ / Discord / Telegram / 微信）下发自然语言指令，Agent 理解意图后驱动无障碍服务完成设备操作，并把过程与结果回传渠道。

与纯聊天机器人的本质差异：**执行环境是真实的**。产品竞争力应建立在"执行得可靠、用得住"上，而不是渠道数量或聊天体验上。

## 2. 现状能力盘点

| 能力域 | 现状 | 成熟度 |
|---|---|---|
| 消息渠道 | 6 渠道接入，均走官方开放平台协议 | 较完整 |
| Agent 内核 | 40–60 轮循环、死循环检测、重试退避、上下文分级压缩、可配置上下文窗口 | 较完整 |
| 设备操控 | 无障碍服务 + 30+ 工具（手机 / TV 两套工具集） | 核心资产 |
| 记忆与个性 | 人格（persona.md）、按发送者会话、长期记忆（memory.md）、技能包（SKILL.md） | 刚落地，待打磨 |
| 任务模型 | 单任务锁 + 排队（上限 3 条） | 最初级 |
| 用户入口 | 仅外部 IM 渠道；设备端无对话界面 | 明显短板 |
| 可观测性 | 仅 logcat；无任务历史与统计 | 空白 |

## 3. 迭代主线

1. **执行可靠性**（M1）：把"失败一次用户就流失"的问题变成可度量、可承诺的指标。
2. **入口与主动性**（M2）：从"配置门槛高的被动机器人"变成"装上即用、每天会自己动"的助手。
3. **能力放大**（M3）：Intent 工具包、多模态观察、技能分发、多设备，拉高天花板。

## 4. 里程碑总览

| 里程碑 | 主题 | 功能 | 优先级 |
|---|---|---|---|
| M1 | 可靠性与信任 | F1 弹窗暂停-恢复、F2 危险操作确认、F3 任务历史与诊断页、F4 结果验证闭环 | P0（F4 可延至 M2） |
| M2 | 入口与主动性 | F5 App 内对话、F6 悬浮球语音、F7 定时/例行任务、F8 事件驱动触发 | F5/F7 为 P0，其余 P1 |
| M3 | 能力放大 | F9 Intent 系统工具包、F10 多模态观察、F11 技能/人格分发、F12 多设备与子 Agent、F13 用量看板 | P1–P2 |

依赖关系：F3（任务历史落盘）是 F13（看板）的数据地基；F7（定时任务）复用 F2 的确认链路与 F3 的可观测链路；F5 的 InAppChannel 是 F12 多设备消息路由的前置抽象。

## 5. 功能详单

### F1 系统弹窗"暂停-恢复"（P0）

**痛点**：受保护系统窗口（如权限弹窗）会同时阻断节点树读取与手势注入。当前实现（`DefaultAgentService` 检测 → `TaskOrchestrator.onSystemDialogBlocked`）是截图发给用户后**直接终止任务**，而权限弹窗恰恰卡在安装、存储、定位等高频场景上，是执行成功率的第一杀手。

**方案要点**：
- 引入"等待人工处理"任务状态：发渠道消息（附截图 + 说明）后任务挂起，不释放会话上下文与剩余轮次。
- 用户处理完系统弹窗后，回复确认关键字（如"继续"）或点击渠道按钮，Agent 从中断点恢复执行。
- 超时兜底：默认等待 5 分钟无响应才终止，终止消息附"如何重新派发"提示。
- 悬浮球新增"待处理"状态（区别于运行中/成功/失败）。

**验收标准**：
- 权限弹窗场景下，用户手动关闭弹窗并回复"继续"后，任务从中断轮次继续而非重跑。
- 超时路径正常终止，会话历史与消息队列不丢失。

### F2 危险操作确认机制（P0）

**痛点**：支付、发送消息、删除、下单等不可逆操作目前可被 Agent 直接执行，缺少信任地基，无法推广到"帮家人操作手机"等场景。

**方案要点**：
- 工具层声明敏感级别：`BaseTool` 增加敏感标记（或注册时声明），覆盖发消息、删除、支付、系统设置变更等。
- 触发即暂停：经渠道发送确认卡片（操作摘要 + 目标 App + 确认/取消指令），用户回复后才执行；超时自动取消。
- 策略可配置：按渠道 / 人格 / 技能调整确认策略（如家庭设备全量确认，个人设备仅支付类确认）。
- 与 F7 联动：无人值守的定时任务默认拒绝执行敏感操作，转为通知用户人工确认。

**验收标准**：默认策略下所有敏感操作均有确认；确认链路不阻塞任务锁与消息队列；定时任务遇到敏感操作有明确的降级行为。

### F3 任务历史与诊断页（P0）

**痛点**：排查"任务为什么失败"目前只能连 logcat，普通用户和远程支持都做不到。

**方案要点**：
- 落盘：每次任务记录一条结构化日志（时间、渠道、发送者、任务文本、轮次、工具调用序列、每轮 token、最终状态、失败原因、关键截图索引），本地 JSONL 或 Room 存储。
- 展示：LAN 配置页（`ConfigServer`，9527 端口）新增"任务历史"卡片，支持按渠道 / 状态 / 时间筛选，点开看完整轨迹。
- 敏感信息脱敏沿用现有 GET 掩码策略；`AgentCallback.totalTokens` 已回传数据，直接积累。

**验收标准**：任意一次任务可在 PC 浏览器回看完整工具轨迹与失败点；连续 100 次任务落盘不影响设备性能。

### F4 结果验证闭环（P1）

**方案要点**：
- 关键工具执行后强制回读断言：`open_app` 后校验前台包名、`click_by_text` 后校验目标节点出现或界面变化。
- 断言失败自动重试一次，再失败才上报，把"看起来执行了"和"确实执行了"区分开。
- 可全局开关，误报率需实测控制在可接受范围。

**验收标准**：开启后核心操作类任务的成功率指标可度量提升；断言失败有明确的遥测记录（进 F3）。

### F5 App 内对话界面（P0，M2 首项）

**痛点**：目前必须先在钉钉/飞书等平台创建机器人并配置凭证才能使用，门槛极高，无法"装上就能玩"，也无法现场演示。

**方案要点**：
- 实现本地 `InAppChannel`（实现现有 `Channel` 接口），完整复用 `TaskOrchestrator`、会话、记忆、技能链路。
- App 内聊天页：RecyclerView（MultiType 已在依赖中）+ 输入框；消息气泡区分用户/Agent/工具摘要。
- 会话与 IM 渠道共用 `SessionStore`（渠道标识为 `in_app`），人格、技能、记忆全部生效。

**验收标准**：零渠道配置的新装用户可在 App 内完成一次完整的多步设备任务；与 IM 渠道互不干扰。

### F6 悬浮球语音输入（P1）

**方案要点**：`FloatingCircleManager` 扩展长按手势唤起系统 `SpeechRecognizer`，识别文本走与 F5 相同的任务入口；识别失败有文字输入兜底提示。

**验收标准**：语音 → 任务派发 → 结果回传（悬浮球 + App 内聊天）端到端可用。

### F7 定时 / 例行任务（P0，M2 核心）

**定位**：从"被动响应"到"主动服务"的关键一跳，是这类产品从玩具变刚需的分水岭（如"每天 8 点把邮件摘要发到飞书群"）。

**方案要点**：
- WorkManager 做调度（复用现有 `KeepAliveJobService` 保活链路），支持 cron 式或自然语言描述（由 Agent 解析为结构化计划）。
- 例行任务 = 调度器 + 渠道/发送者绑定 + 指令或技能（技能系统天然承接）。
- 执行结果主动推送到绑定渠道；任务记录进 F3 历史链路。
- `BootReceiver` 重启后恢复全部计划；设备不可用（锁屏限制等）时按策略降级并通知。

**验收标准**：重启后定时任务全部恢复；无人值守执行与手动任务走同一可观测链路；敏感操作有 F2 确认或降级。

### F8 事件驱动触发（P2）

> 已落地（2026-09-04）：`trigger/` 纯 JVM 包（TriggerRule/TriggerConfig 校验 + TriggerRuleEngine 正则匹配 + TriggerRuleStore 落盘）+ `TriggerNotificationListener`（通知监听）+ `GET/POST /api/trigger` + LAN 页"事件驱动触发"卡片。默认关闭（总开关关、白名单/规则空）；触发任务走 `automated=true` 进入 C3 频控/静默/熔断与 F3 留痕；系统侧还需授予"通知使用权"（LAN 页展示授权状态）。
> 真机端到端验收已通过（同日）：adb 授予通知使用权 → shell 测试通知 → 规则命中提取验证码 → automated 派发过 C3 准入 → F3 历史留痕（`trig-*`）。验收当日设备上的 LLM key 出现"身份验证失败"（积分 key 余额/有效期问题，与 F8 链路无关）。

**方案要点**：`NotificationListenerService` 监听白名单 App 的通知（如短信验证码），规则匹配后触发对应技能（如自动填入验证码）。默认关闭 + 显式白名单 + 每次触发留痕（进 F3）。

**验收标准**：验证码自动填入场景端到端跑通；白名单与触发记录用户可见可控。

### F9 Intent 系统服务工具包（P1）

**思路**：联系人、日历、闹钟、媒体控制、Wi-Fi/蓝牙/亮度/音量等系统能力，走系统 Intent / API 比模拟 UI 点击可靠一个数量级，且不涉及第三方 App。

**方案要点**：
- 新增系统工具组（工具实现放 `tool/impl/`，沿用 `BaseTool` 抽象）：联系人查询、日历增删查、闹钟/计时、媒体控制、亮度/音量/勿扰、拨号盘预填（不自动拨出）等。
- 系统提示词中明确工具选择优先级：**系统服务工具 > UI 自动化**；`ToolRegistry` 按设备能力注册。

**验收标准**：覆盖 10+ 系统能力；实测中 Agent 在两类工具并存时优先选择 Intent 工具。

### F10 多模态观察（P1）

**方案要点**：
- `take_screenshot` 结果作为图像消息进入 LLM 上下文（OpenAI / Anthropic 视觉接口均支持）。
- 触发策略：节点树不可用、解析置信度低、或模型主动请求时才截图（按需截图控制 token 成本）。
- 优先覆盖节点树读不到的场景：自绘 UI、WebView、游戏。

**验收标准**：至少一个纯视觉场景（如 WebView 内导航）可完成任务；单任务截图数量有上限。

### F11 技能 / 人格分发与市场（P1）

**方案要点**：
- 技能包导出/导入：zip 打包 + URL 下载 + 二维码导入（ZXing 已在依赖中）。
- 内置模板库：常用场景技能（如"会议纪要整理""相册清理"）与人格模板。
- 导入安全审查：技能本质是提示词注入载体，导入时做提示注入风险扫描与来源提示；人格市场同策略。

**验收标准**：扫码导入端到端可用；含恶意指令样例的技能包能被扫描拦截或显著告警。

### F12 多设备与子 Agent（P2）

**定位**：从"遥控一台手机"升级为"个人设备舰队"（手机 + 家庭 TV），是与同类产品拉开差距的方向。

**方案要点**：
- 设备注册中心：设备 ID / 名称 / 能力集（手机 / TV 工具集已按设备类型区分）。
- 渠道消息支持指定目标设备（"让客厅电视……"），未指定时按规则路由或追问。
- 任务锁从全局单任务改为**按设备粒度**的锁池；跨设备任务由主 Agent 拆解为子 Agent 派发与汇总。

**验收标准**：两台设备（一手机一 TV）在同一 bot 下可并行派发互不阻塞的任务。

### F13 用量与成本看板（P2）

> 已落地（2026-09-04）：`stats/UsageStatsAggregator`（纯 JVM 聚合，日/渠道/发送者/高频任务 Top N）+ `GET /api/stats?days=N` + LAN 页"用量看板"卡片（日 token 曲线、成功率、渠道统计）。数据源为 F3 任务历史（`task_history.jsonl`，最多保留 200 条）；发送者仅显示前 6 位。

**方案要点**：基于 F3 的落盘数据，按日 / 渠道 / 发送者聚合 token 消耗与任务成功率，LAN 页新增统计卡片。为将来订阅或按量模式积累数据。

**验收标准**：日 token 曲线、任务成功率、高频场景 Top N 展示可用。

## 6. 账号安全与平台合规设计

**风险认知**：本产品的操作对象包含第三方 App，部分平台（尤其社交类）的反自动化风控可能判定自动化行为并封禁用户账号。**账号安全是本产品形态的固有风险，产品策略是"从源头减少触发风控的可能"，而不是对抗或绕过平台的检测机制。**（落地实现、默认值与设置说明见 `docs/COMPLIANCE.md`）

明确的原则：**不做对抗平台检测的功能**（如隐藏无障碍服务特征、拟人化行为伪装以欺骗风控分类器等）。理由：
1. 对抗检测等于把用户的账号押在一场打不赢的军备竞赛上，平台升级即失效，且被识别后处罚更重；
2. 违反平台服务条款，损害用户利益与项目（开源）声誉；
3. 产品真正的护城河是官方 API 集成与系统能力整合的可靠性，不在灰色地带。

据此落实以下六项设计（部分与功能项合并）：

| # | 措施 | 说明 | 关联 |
|---|---|---|---|
| C1 | **官方 API 优先** | 消息渠道全部走官方开放平台（钉钉 Stream、飞书 OAPI、QQ Bot、Discord Gateway、Telegram Bot API、微信官方 bot）；新增能力一律先找官方接口，UI 自动化只是兜底 | 渠道层（已达成，保持） |
| C2 | **操作场景分级** | 一级场景：系统应用与设备设置（Intent/系统 API，无第三方风控）；二级场景：第三方 App 的 UI 自动化，默认保守策略 | F9 |
| C3 | **频控与人速** | 全局与按渠道的操作频率上限、任务间冷却间隔、夜间静默时段、连续失败熔断。目的：避免高频异常操作触发平台风控，同时保护设备与电量 | 新增设置项 |
| C4 | **不可逆操作人工确认** | 发送、支付、删除类操作默认经用户确认，既防误操作也避免"非本人意愿的自动化行为" | F2 |
| C5 | **用户知情与授权** | 设置页对二级场景（第三方 App 自动化）做明确风险提示与单独开关；文档列明各平台条款风险，用户知情后自担 | 设置页 |
| C6 | **按 App 自动化策略** | 允许用户（或技能）为单个 App 配置策略：仅系统 App 全自动；社交/支付类 App 强制确认或默认禁用 | F2 延伸 |

## 7. 度量指标

- **北极星**：周活跃发送者的周完成任务数。
- **可靠性**：任务一次完成率、弹窗恢复成功率（F1）、确认后执行完成率（F2）。
- **入口**：新装用户"零配置首任务"完成率（F5 上线后）。
- **主动性**：日均主动（定时/事件）任务数（F7/F8 上线后）。
- **成本**：单任务平均 token、月度设备均成本（F13）。

## 8. 建议节奏

| 阶段 | 内容 | 目标 |
|---|---|---|
| M1 | F1 + F2 + F3（+F4） | 任务成功率可度量、可信、可排障 |
| M2 | F5 + F7（+F6、F8） | 装上即用、每天会自己动 |
| M3 | F9 + F10 + F11（+F12、F13） | 覆盖率、生态与社区起飞 |
